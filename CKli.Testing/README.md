# CKli.Testing

**CKli.Testing** is the test-helper library for CKli. It provides everything an integration test needs to stand up a
realistic, disposable, multi-repository CKli scenario — fake Git remotes, a cloned Stack with Repos, and small
helpers to mutate them — without touching a real GitHub/GitLab/Gitea server or leaving state behind between test runs.

It ships as a plain NuGet-style project (`CKli.Testing.csproj`, `net10.0`) referencing `CKli.Loader` and
`CK.Testing.NUnit`, and is meant to be added as a `ProjectReference` from a test project (see [How a consuming
project is laid out](#how-a-consuming-project-is-laid-out) below).

The whole library is three files:

| File | Role |
|---|---|
| [`CKliTestHelperExtensions.cs`](CKliTestHelperExtensions.cs) | Static bootstrap + extension methods on `IMonitorTestHelper` (`InitializeClonedFolder`, `OpenRemotes`, `TouchAndCommit`, `CKliCreateRemoteFolderFromCloned`). |
| [`CKliTestHelperExtensions.RemotesCollection.cs`](CKliTestHelperExtensions.RemotesCollection.cs) | The nested `RemotesCollection` class: describes one fake-remote Stack (+ its Repos) and clones it. |
| [`ClonedFolder.cs`](ClonedFolder.cs) | The `ClonedFolder` class: a per-test working directory, with helpers to create bare/orphan repositories directly in it. |

## Why

CKli's core model — a Stack repo, a World XML file, N Repos, plugin configuration, `$Local` state — is inherently
stateful and disk/Git-based (see `CKli.Core/README.md`). Exercising commands like `ckli build`, `ckli fix start`,
`ckli publish` end-to-end means, for every test:

- having real Git remotes to clone from and push to (a plain local folder isn't enough: CKli's push/pull logic,
  branch model, and hosting-provider abstraction expect actual remote semantics — a **bare** repository);
- cloning a full Stack + its Repos into a scratch folder;
- getting the World's `<Plugins>` configuration wired the same way the host project's own Stack is configured, so
  plugin behavior under test matches production configuration;
- resetting all of the above between tests, cheaply, without hitting the network.

`CKli.Testing` solves this by keeping two on-disk areas per test project, next to the test project file itself
(`TestHelper.TestProjectFolder`):

- **`Remotes/`** — canonical fake remotes. A `Remotes.zip` (the only thing committed to source control) is unzipped
  once, and from the unzipped non-bare repositories a `bare/` folder of true bare repositories (`core.bare = true`)
  is derived and re-zipped per stack-state (`bare/<FullName>.zip`). `OpenRemotes(fullName)` always deletes and
  re-extracts the `bare/<FullName>` folder from its zip before handing it out, so every test starts from a pristine,
  unmodified "remote" regardless of what a previous test pushed to it.
- **`Cloned/`** — disposable per-test working folders, one subfolder per test method
  (`Cloned/<TestMethodName>/`), cleaned (or created) by `InitializeClonedFolder()`.

This mirrors exactly what's documented in the consuming test project's own `Remotes/README.md` (see
`Tests/Plugins.Tests/Remotes/README.md` in `CKli-Plugins`): the zip is unzipped, bare repos are rebuilt from the
unzipped `.git` folders, and each `OpenRemotes` call resets the `bare/` folder from its zip archive so pushes made
by one test never leak into the next.

## How

### Static bootstrap

`CKliTestHelperExtensions` has a static constructor that runs once per test assembly load and:

1. Computes `Remotes/`, `Remotes/bare/` and `Cloned/` under `TestHelper.TestProjectFolder`.
2. Derives the default `WorldName` from the test project's folder name (it must contain `-Plugins`, e.g.
   `CKli-Plugins` → stack `CKli`), and reads that host Stack's own `<WorldName>.xml` `<Plugins>` element
   (`_hostPluginsConfiguration`) — this is the "production" plugin configuration later injected into every cloned
   test World. It throws if that element is missing or if any plugin in it is `Disabled="true"`.
3. Calls `CKliRootEnv.Initialize(...)` once for the whole test run.
4. Locates the compiled plugins assembly (`CKli.CompiledPlugins.cs` / `CKli.Plugins.dll`, generated by the plugin
   compilation pipeline for the `-Plugins` solution) and wires `World.DirectPluginFactory` to it — tests load
   plugins the same way `ckli` does at runtime, not through source recompilation.
5. Calls `InitializeRemotes()`, which unzips `Remotes.zip` (only if `bare/Remotes.txt`'s timestamp doesn't match
   `Remotes.zip`'s), rebuilds `bare/<stack>/<repo>` bare repositories and their per-stack `.zip`, and returns a
   `Dictionary<string, RemotesCollection>` keyed by "full name" (stack name, optionally suffixed with a
   parenthesized state, e.g. `"CKt(init)"`, `"CKt(initialized)"`).

Because of this static initializer, simply referencing the assembly from an NUnit test project — and calling
`TestHelper.InitializeClonedFolder()` / `TestHelper.OpenRemotes(...)` — is enough to get the whole fake-remote
machinery ready.

### `RemotesCollection`

Models one `Remotes/<FullName>/` entry: a `<StackName>-Stack` repository plus the Repos it references.

```csharp
public sealed partial class RemotesCollection
{
    public string FullName { get; }                 // e.g. "CKt(initialized)"
    public string StackName { get; }                 // e.g. "CKt"
    public Uri StackUri { get; }                      // bare/<FullName>/<StackName>-Stack
    public IReadOnlyList<string> Repositories { get; } // all repo folder names, incl. "<StackName>-Stack"

    public Uri GetUriFor( string repositoryName );    // bare/<FullName>/<repositoryName>, or a "Missing..." fake url

    public Task<CKliEnv> CloneAsync( ClonedFolder clonedFolder,
                                      Action<IActivityMonitor, NormalizedPath, XElement>? pluginConfigurationEditor = null,
                                      bool privateStack = false );

    public Task<CKliEnv> CloneAsync( NormalizedPath folder, bool allowDuplicateStack,
                                      Action<IActivityMonitor, NormalizedPath, XElement>? pluginConfigurationEditor = null,
                                      bool privateStack = false );
}
```

You obtain one with `TestHelper.OpenRemotes("CKt(initialized)")` — this also resets the corresponding `bare/`
folder from its zip, as described above.

`CloneAsync` is the workhorse:

1. Clones the Stack from `StackUri` into the `ClonedFolder` (into `.PublicStack/` or `.PrivateStack/` depending on
   `privateStack`), opens its default World (`skipPullStack: true`, `withPlugins: false`).
2. Overwrites the cloned World's `<Plugins>` element with the host project's own `<Plugins>` configuration
   (`_hostPluginsConfiguration`), then invokes the optional `pluginConfigurationEditor` callback so a test can
   further tweak plugin XML before anything loads. Commits that change to the (local) cloned Stack repo.
3. Copies the `Remotes/<FullName>/<StackName>-Stack/$Local` folder, if any, into the clone's `$Local` — lets a
   fixture ship pre-baked local-only state (e.g. secrets, caches) alongside the remote.
4. Returns a ready-to-use `CKliEnv` positioned at the cloned Stack root.

The `NormalizedPath`-based overload (with `allowDuplicateStack`) exists to clone the same remote a second time into
a sub-folder of an already-initialized `ClonedFolder` (`allowDuplicateStack: true` avoids the duplicate-stack
detection that would otherwise throw).

### `ClonedFolder`

A thin wrapper around one `Cloned/<TestMethodName>/` path, returned by `InitializeClonedFolder()`. Besides exposing
`Path`, it offers instance and static helpers to create ad hoc Git repositories directly inside that folder, outside
of any `RemotesCollection`/Stack flow — useful for tests that need a standalone bare or orphan repository:

```csharp
public sealed class ClonedFolder
{
    public NormalizedPath Path { get; }

    public GitRepository CreateBareRepository( string repositoryName, out Uri repositoryUrl );
    public GitRepository CloneGitRepository( string name, Uri remoteUrl );
    public GitRepository CreateOrphanGitRepository( string repositoryName );

    // Static equivalents taking an explicit `NormalizedPath folder` instead of using `Path`.
}
```

- `CreateBareRepository` inits a bare repo with `main` as initial branch, one empty commit, and origin url
  `GitRepositoryKey.BareRepositoryFakeUrl` (`file://Bare-Fake-Remote/`).
- `CreateOrphanGitRepository` does the same but with `GitRepositoryKey.OrphanRepositoryFakeUrl`
  (`file://Orphan-Fake-Remote/`) — an orphan repo has no real remote at all.
- `CloneGitRepository` clones from an explicit `remoteUrl` (typically a `RemotesCollection.GetUriFor(...)` /
  `StackUri`, or a bare repository created above).

### Other `IMonitorTestHelper` extension members

| Member | Purpose |
|---|---|
| `helper.CKliRemotesPath` | The `Remotes/` folder. |
| `helper.CKliClonedPath` | The `Cloned/` folder. |
| `helper.CKliDefaultWorldName` | The host project's default `WorldName`, derived from the test project's folder name. |
| `helper.CKliStackWorkingFolder` | `helper.SolutionFolder` (the `.PublicStack`/`.PrivateStack` folder of the *host* stack — the real one the plugin solution lives in, not a test clone). |
| `InitializeClonedFolder(methodTestName?, clearStackRegistryFile = true)` | Cleans/creates `Cloned/<methodTestName>` (defaults to `[CallerMemberName]`, i.e. the test method) and returns a `ClonedFolder`. Clears CKli's global stack registry file by default so each test starts with no stacks known. |
| `OpenRemotes(fullName)` | Resets `bare/<fullName>` from its zip and returns the matching `RemotesCollection`. |
| `TouchAndCommit(folder, branchName, commitMessage?, fileContent?, fileName = "CKliTouchAndCommit.txt", authorAndCommitWhen?)` | Appends/creates a file and commits it — either on the current working-folder head (`branchName: null`), on the branch if it's already checked out, or directly as a new commit object on a non-checked-out branch (via `TreeDefinition`/`ObjectDatabase`, no checkout needed). Committer signature is always `"CKli.Testing" <none>`. |
| `CKliCreateRemoteFolderFromCloned(builderMethodName, stackName, testStateName)` | Turns a finished `Cloned/<builderMethodName>` into a brand-new `Remotes/<stackName><testStateName>` fixture: strips all `origin` remotes, copies the Stack + every Repo's working folder as-is, then re-initializes the source cloned folder. Used to *author* new fixture states (see below); does **not** update `Remotes.zip` — that's done separately with `ZipRemotes.ps1` in the consuming test project. |

## Usage

From `Tests/Plugins.Tests` (the `CKli-Plugins` repo), a typical test:

```csharp
[Test]
public async Task local_fix_Async()
{
    Helper.SetFileSystemWritePAT();
    var clonedFolder = TestHelper.InitializeClonedFolder();
    var remotes = TestHelper.OpenRemotes( "CKt(initialized)" );
    var context = await remotes.CloneAsync( clonedFolder, Helper.ConfigureFakeFeeds ).ConfigureAwait( false );
    var display = (StringScreen)context.Screen;

    var cktCoreContext = context.ChangeDirectory( "CKt-Core" );

    (await CKliCommands.ExecAsync( TestHelper.Monitor, cktCoreContext, "fix", "start", "v1.0" )).ShouldBeTrue();
    display.ToString().ShouldBe( """
        Fixing 'v1.0.0' on CKt-Core:
        ...
        """ );

    TestHelper.TouchAndCommit( cktCoreContext.CurrentDirectory, branchName: "fix/v1.0" );
    // ...
}
```

`Helper.SetFileSystemWritePAT()` and `Helper.ConfigureFakeFeeds` above are project-local helpers in `Plugins.Tests`
(not part of `CKli.Testing`) that configure the `FileSystemProvider` hosting PAT and fake NuGet feeds respectively —
`CKli.Testing` only provides the remote/clone/commit machinery; per-domain fixtures (feeds, PATs, sample project
files) are the consuming project's responsibility.

`CKliCommands.ExecAsync(monitor, context, "issue")`, `"build --ci --dry-run"`, `"publish"`, etc. are then run
against the cloned `CKliEnv`, and `(StringScreen)context.Screen` captures the rendered output for assertion (via
`display.ToString().ShouldBe("""...""")`), following `CKli.Core`'s `IScreen`/`StringScreen` testing abstraction.

Building a *new* fixture state typically pairs an `[Explicit]` test with the normal one, e.g.:

```csharp
[Explicit]
[Test]
public async Task REMOTES_CKt_init_to_initialized_Async()
{
    FileHelper.DeleteFolder( TestHelper.Monitor, TestHelper.CKliRemotesPath.AppendPart( "CKt(initialized)" ) );
    await CKt_init_Async();
    TestHelper.CKliCreateRemoteFolderFromCloned( "CKt_init_Async", "CKt", "(initialized)" );
}
```

`CKt_init_Async` runs the normal scenario against `Cloned/CKt_init_Async/`, then
`CKliCreateRemoteFolderFromCloned` promotes that resulting folder to a new `Remotes/CKt(initialized)/` fixture
(stripping remotes first). It's `[Explicit]` because it mutates the checked-in fixture set and must be run
deliberately, then followed by `ZipRemotes.ps1` to refresh `Remotes.zip`.

## How a consuming project is laid out

Based on `Tests/Plugins.Tests` (`CKli-Plugins`) and `Tests/CKli.Core.Tests` (`CKli`):

```
<Something>.Tests/
├── <Something>.Tests.csproj   ← ProjectReference to CKli.Testing.csproj
├── Remotes/
│   ├── .gitignore              ← "* / !.gitignore / !Remotes.zip / !ZipRemotes.ps1 / !README.md"
│   ├── README.md                ← explains the zip/bare mechanism to humans
│   ├── Remotes.zip              ← the only committed artifact; non-bare repos, one folder per FullName
│   ├── ZipRemotes.ps1           ← script to re-zip Remotes/<FullName> folders back into Remotes.zip
│   └── bare/                    ← generated, gitignored: bare repos + Remotes.txt index
└── Cloned/                      ← generated, gitignored: one folder per test method
```

The `.csproj` must exclude both folders from compilation and treat them as content, since the NUnit test adapter
otherwise discovers `.csproj`/test-like files inside them:

```xml
<ItemGroup>
  <None Include="$(Content);Remotes\**;Cloned\**" />
  <Compile Remove="Remotes\**;Cloned\**" />
</ItemGroup>
```

The test project's folder name must contain `-Plugins` (e.g. `CKli-Plugins`) — the static bootstrap derives the
default `WorldName` and the compiled-plugins assembly path from it (`PluginMachinery.GetPluginSolutionName` /
`GetLocalRunFolder`), and expects `CKli.CompiledPlugins.cs` / `CKli.Plugins.dll` to already exist (run
`ckli plugin info` in the host stack if they're missing).

## Notes / open points

- The `-Plugins` folder-name convention and the `$(ltsName)`-derived shared/local data folders (`sharedDataFolder`,
  `localDataFolder` in the static constructor) tie this library specifically to the CKli plugins-solution layout;
  it isn't a generic "spin up any Git repos" helper.
- `RemoteCollection.CloneAsync`'s `allowDuplicateStack` / duplicate-stack detection and `StackRepository.DuplicatePrefix`
  are only lightly documented in the XML comments here — see `StackRepository` in `CKli.Core` for the full picture
  if you need to clone the same remote twice into one `ClonedFolder`.
